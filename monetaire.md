# Monetaire - Personal Finance Classifier

Monetaire is a personal finance classifier of which I am the only user. Since I am the only user and I want it to run under my own infrastructure, all the information it contains is only to be stored locally. In other words, it never leaves my machine unless I backup the data. It is cross-platform but with a preference for Unix systems, not Windows. This project aims to classify and store finances, aggregating results over time and making them easier to visualize. The end-goal and future vision is not only for me to be able to see my finances and perform simulations for rentability and net value, but also for it to be integrated with local AIs that will learn from me and my spending and suggest areas of improvement. This would be integrated with actual financial information like Brazilian up-to-date income taxes, CDI rates, inflation, etc. This AI would obviously be local-only, and it would never leave my computer, since it is actively learning from sensitive information. Monetaire should be lightning fast and easy to use. It should not take long to start and it should be very responsive, given the data lives in my computer. At the same time, the application should be generic enough that, should I wish to market this as a product in the far off future, I would be able to do so transporting it to the web without much of a hassle, whilst still keeping things private. We can do this by leveraging web UI technologies with version pining: we avoid upgrading our libraries until we know they're safe: that is, we only upgrade once every 6 months, and at that, we use a version at least a month old of the library. This is because of the great degree of vulnerabilities that web technologies have, and the immense potential for supply chain attacks. We are to think very thoroughly in terms of security in that sense, leveraging best practices here. This isn't a child's play application, it is serious business, even if I am the only user thereof. Where possible and feasible (i.e. the work would not be too great) it is preferred we build our own ad-hoc versions of lirbaries instead of using more and more dependencies, but prudence should be used to decide, carefully evaluating pros and cons. We should always perform threat modelling and a software bill of materials, succint but informative, to know and understand which dependencies we have and where the biggest threats lie. The application should have a beautiful design, easy to look at, whilst not falling pray to over-design - avoiding emojis and visual fluff unless this is explicitly called for or the features could benefit from them. The application should be able to deal with my income, taking count of the taxes therein; of my expenses in the form of credit card expenditures and manually-inserted expenses; it should further consider how much I have in investments for the future vision; and more features we can buid. The project should always be built in a TDD approach in terms of Red-Green-Refactor. All features should be tested in integration tests that rollback the data when they finalize in order to not break the data on the database when such features require changes to the data layer; all the interfaces to view layer should be thoroughly tested in terms of their specification (whether they're performing the proper validation, etc.), not so much their functionality; and if there are any business logic engines to perform calculations and data transformations that could go wrong, they should be thoroughly tested with unit tests and mock. Only then can the implementation begin, as in good TDD practice. The database should be simple, lightweight and quick and cross-platform also. Database design should follow best practices and be documented in terms of the relationships between tables and what they're for. For heavy development with whatever UI frameworks chosen, documentation should be consulted on the web when things don't seen to be working properly, but not required initially when developing a feature unless the agent developing it thinks it necessary to double-check.
